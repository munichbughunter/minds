# Command Reference

`minds` captures the context of AI-agent coding sessions in Git — intent, attribution, redaction, evidence chain, and reviews — and makes it queryable from the terminal. `minds --help` prints the same command list in the terminal.

## Setup

### minds enable

```
minds enable [--agent <name>] [--child-repo <path>] [--child-remote <url>] [-v] [--ref <name>] [--recall] [--global-hooks]
```

Prepares the repository for Minds: registers the hooks with the agent and the repo, and writes the store config to `.git/config`. Runs silently; `-v`/`--verbose` shows each step. Without `--agent` it configures the agents that look installed — their directory in the repository or in `$HOME` (`.claude`, `.codex`, `.cursor`, `.gemini`, `.config/opencode`) or their executable under an absolute `PATH` entry (`claude`, `codex`, `cursor-agent`/`cursor`, `gemini`, `opencode`), and says which (`minds: hooks set up for …`); when none is found, all known agents (`claude-code`, `codex`, `cursor`, `gemini`, `opencode`, `all`); the command is idempotent and leaves third-party hooks untouched. `--child-repo` places the context in a separate repository instead of in-repo (created bare, or cloned from `--child-remote`); `--recall` (Claude Code) adds an opt-in SessionStart hook that prepends the context brief from previous sessions to a new session (costs tokens); `--global-hooks` confirms a hooks directory outside the repo (e.g. a globally set `core.hooksPath`) — without the flag, enable asks or aborts.

```
minds enable --agent claude-code -v
```

**Protected, on request.** On a terminal, `enable` first asks once: *Set up the witness
protected (administrator rights, once)? [Y/n]*. Yes (or `MINDS_WITNESS=protected`) sets up
the witness under its own user — the only setup that can reach A2:

1. As you, without rights and without widening anything: `core.sharedRepository=group`,
   and `.git/logs` and `.git/minds` exist. Repositories under `~/Desktop`, `~/Documents`,
   `~/Downloads`, `~/Pictures`, iCloud or `/Volumes` are refused on macOS (TCC keeps them
   from system services).
2. One `sudo -k /bin/sh -c <script>` (`-k`: always your password — a cached one does not count, and none is left for the agent) — the script is generated by minds, every value quoted in a
   single pass (`-v` prints it). Root never follows a path you could have planted: each
   system directory is checked to be root's alone (owner, mode, no ACL) before anything is
   written into it, and everything inside your repository and home is done **as you**
   (`sudo -u`). The script: copies the binary — read by you, so a file you cannot read
   cannot be copied — root-owned to `/usr/local/libexec/minds/minds`; creates the user and
   group `_minds` (macOS, hidden, id 300–399) or `minds-witness` (Linux) — the group's members
   are the witness and you (Linux: in new sessions after your next login); as you, lets the
   witness user pass your directories above the repository (an ACL entry, search only) and
   list its root, moves `.git`, `.git/minds` and `objects/`, `refs/`, `logs/` to that group and
   only then makes them group-writable (`.git` with the sticky bit: the group may create lock
   files but not replace your files; `config`, `hooks/`, `info/` and your local journal stay
   yours alone); checks that the witness user can write there; creates its home under
   `/private/var/db/minds-witness/<repo-id>` (macOS) or `/var/lib/minds-witness/<repo-id>`
   (Linux) — `witness init --profile user --socket-group <group>` (with
   `--intent-key <your .pub>` when `git config minds.intentKey` names a security key — a key
   of its own for approving intents, **not** your commit-signing key: a touch for a signed
   commit the agent triggered would otherwise count as an approval. `enable` prints its full
   `SHA256:` fingerprint before asking for the password: compare it with your security key's
   (`ssh-keygen -l` at creation), **not** with the `.pub` next to it — the Git config and that
   file are writable for the agent; a key pinned earlier is kept;
   afterwards `enable` prints `intent key at the witness: …`, computed by the witness user —
   the line to compare), `keygen` and `signers` as that user; installs and starts a system service (`/Library/LaunchDaemons/dev.minds.witness.<repo-id>.plist`,
   its stderr in `<witness home>/log/witness.err`,
   or `/etc/systemd/system/minds-witness-<repo-id>.service` with `NoNewPrivileges`,
   `ProtectSystem=strict`; umask 007); and writes Claude Code managed settings with deny rules
   only (`minds witness`, `Edit` of `.git/refs/minds`, `Read`/`Edit` of the witness home — Claude
   Code checks file access only against `Read(…)`/`Edit(…)`, and `Edit` covers every
   file-writing tool; a file minds installed earlier, in exactly its own form, is merged — the
   rules of other repositories stay and only accumulate; delete the file by hand to clean up) — only
   if no
   `managed-settings.json` exists or it is minds' own; any other file gets a
   `managed-settings.minds-proposed.json` next to it.
3. `enable` waits for the witness (a slow first start is reported, not replaced by the local
   witness), stops and disables the local user service of this repository (if any), and
   prints the witness key's `allowed_signers` line. Its principal is
   `minds-witness-user@<host>` only if the witness passed the separation checks. The line
   is recorded in your trusted signers file (below); an auditor keeps it in a file of
   their own and passes that to `minds verify --signers`.

Hooks find the protected witness at its fixed place without `MINDS_WITNESS_SOCKET` — only if
every directory above it belongs to root, its home to a user other than you, and the socket's
peer is exactly that user. A later `enable` keeps a running protected witness and says so
when it runs another `minds` binary than the one you call (rerun with
`MINDS_WITNESS=protected` to update it). In a repository shared this way, `minds` itself
writes with umask 002 when it writes into the store under `.git` (`hook`, `checkpoint`,
`sync`, `forget`, `import`, `intent`, `spec`, `review`, `sign`, `anchor`, `reinterpret` — not
`enable` or exports), so what it creates stays writable for the witness group. No (or no
terminal, or a failed setup) sets up the local witness below, with a warning. Nothing is
removed again automatically (no `minds disable` yet).

**The trusted signers file and your intent key.** Every `enable` (unless
`MINDS_WITNESS=off`) also sets up, once per user:

- `~/.config/minds/allowed_signers` (`$XDG_CONFIG_HOME/minds/allowed_signers`): the
  witness key's line (`namespaces="minds-witness"`) is appended if it is not there yet —
  idempotent, nothing to copy —, and `git config --global minds.signers` points at the
  file. `minds verify`, `minds inspect`, `minds fsck` and `minds audit` take it as the
  default signer file (`--signers` overrides; `verify` prints `Signers <file> (<source>)`
  first). The file lives in your home, where an agent under your user ID can write it:
  an auditor keeps their own copy outside the agent's reach.
- `~/.config/minds/intent_ed25519`: an ed25519 software key without passphrase, set as
  `git config --global minds.intentKey`, its `namespaces="minds-intent"` line (principal:
  your `user.email`, else `<user>@<host>`) appended to the signers file. `minds intent
  sign` without `--key` uses it. A security key (FIDO) stays opt-in: with `minds.intentKey`
  already set to another key, no key is created.

**The witness, by default.** Without `--witness`, `enable` always sets up a witness for
this repository (profile `local`): `minds witness init --profile local` and a key in the
witness home (`MINDS_WITNESS_HOME`, otherwise `$XDG_STATE_HOME/minds-witness/<repo-id>`),
the user service (`~/Library/LaunchAgents/dev.minds.witness.<repo-id>.plist`, or
`$XDG_CONFIG_HOME/systemd/user/minds-witness-<repo-id>.service`), started with
`/bin/launchctl` (an already loaded job of that name is unloaded and loaded from this file)
or `systemctl --user` (refused when the unit has drop-ins or comes from another file) —
absolute paths, never a privileged command. `enable` reports success only after the
witness answers on its socket. Hooks and the commit checkpoint find it at
`run/witness.sock` in that home when `MINDS_WITNESS_SOCKET` is not set
(`MINDS_WITNESS_HOME` counts only when it is absolute) — only a home whose `witness.json`
pins this repository with profile `local`, owned by you and writable by no one else, only
when the witness answering on the socket runs under your user ID, and only for events whose
working directory lies in this repository; a witness of another profile is reached only
through an explicit `MINDS_WITNESS_SOCKET`. Each `enable` pins the redaction policy of the
`local` witness anew from `.minds/redact.json` at HEAD, so a later committed policy applies
after the next `enable`.

It runs under **your** user ID: it witnesses, but an agent with a shell could stop it or
read its key — `enable` prints a yellow `warning:` saying so, `minds doctor` reports the
profile as a warning, and the assurance stays at A1 (`observed`); only a witness under its
own user (or a qualified container) reaches A2. Its key is not a protected witness key —
do not add its `allowed_signers` line for A2. Raw hook events live in the witness home
(outside the repository) until they are sealed into the store.

A witness home that pins another repository (e.g. a globally exported
`MINDS_WITNESS_HOME`) is refused with a warning (`minds doctor` reports it as a failure); an
existing setup with another profile (e.g. `--witness container`) is left as it is and not
started — except a home owned by your user ID that claims profile `user` (such a witness
runs under its own user), which `enable` warns about. A `minds` binary inside the
repository or in a build directory (`target/debug`, `target/release`) is refused — another
checkout rewrites it. `MINDS_WITNESS=off` skips the witness (the test suites use it),
`MINDS_WITNESS=local` (or `on`) sets it up without asking, `MINDS_WITNESS=print` sets it up
and prints the start command instead of running it. With
`MINDS_WITNESS_SOCKET` set (e.g. inside a dev container), no local witness is set up; a
relative `MINDS_WITNESS_HOME` and running as root are refused with a warning. If
anything fails (binary, no service manager, a differing service file, a witness that does
not answer), `enable` warns with the cause and still succeeds; hooks then record into the
local journal. Each linked worktree has its own repository id, hence its own witness.

### minds enable --witness

```
minds enable [--agent <name>] --witness container|user|managed
```

Runs the normal `enable` steps first, then sets up a witnessed configuration. No step runs a privileged command, no existing file is overwritten — when a file already exists with different content, `<name>.minds-proposed` is written next to it and the report says so — and no service is started. Reruns are idempotent.

- **`container`** (run on the host, in the repository): `minds witness init` with `--path-map /workspaces/<name>=<root> --profile container` and `minds witness keygen` (skipped when the key pair exists; an incomplete pair stops `enable` — remove `key/witness_ed25519*` and rerun) in the witness home (`MINDS_WITNESS_HOME`, otherwise `$XDG_STATE_HOME/minds-witness/<repo-id>`; it must lie outside the repository, symlinks resolved). Writes `.devcontainer/devcontainer.json` and `.devcontainer/compose.yaml` from the EA-S2 templates, which mount only `$MINDS_WITNESS_HOME/run` at `/run/minds-witness` and set `MINDS_WITNESS_SOCKET`. Installs a user service — `~/.config/systemd/user/minds-witness-<repo-id>.service` on Linux, `~/Library/LaunchAgents/dev.minds.witness.<repo-id>.plist` on macOS — and prints the exact command to enable it. If a different service file already exists, it is left alone, the template goes next to it as `*.minds-proposed`, and the report asks you to review and move it into place before starting. The service file must not lie inside the repository. Prints the host variables Compose needs and the witness key's `allowed_signers` line: keep it in a file outside the repository that the team distributes out of band, and pass that file to `minds verify --signers`. The report also shows the pins `init` recorded (git dir, store, policy source). The service runs the `minds` binary you ran `enable` with; a binary inside the repository (e.g. `target/release/minds`) or a writable one with more than one hard link is refused, because the agent could replace it and the service would run it on the host. A child-repo store is pinned only from `--child-repo` given to this `enable`, never from `.git/config` alone. `.devcontainer/` is part of the isolation boundary and lives in the agent-writable repository: review every change to it; `minds doctor` on the host fails when `.devcontainer/` holds anything but the two unchanged templates (and `*.minds-proposed`), e.g. a `.env` or a second `devcontainer.json`, or when `.devcontainer.json` exists at the repository root. On macOS, container recording stays unqualified until the EA-S2 measurements pass.
- **`user`**: prints the exact steps for a dedicated OS user `minds-witness` and group `minds-agents` (install minds from a verified release artifact, never from the agent's account; home ownership with group traverse on `/var/lib/minds-witness`; sharing the repository with the group as its owner, never as root, inside a block that stops on a planted symlink; socket group; `witness init --profile user --socket-group minds-agents`) including the systemd unit for that user. Nothing is executed.
- **`managed`**: writes only `managed-settings.minds-proposed.json` (the EA-S1 settings, aimed at this repository's witness home, `.claude/` and binary) with a `$comment` header: the profile yields A1 until EA-S1 says otherwise. Paths with glob or rule metacharacters are refused, since a rule could not protect them. The file lies in the agent-writable repository, so the report prints its BLAKE3 digest: compare it before installing.

```
minds enable --agent claude-code --witness container
```

### minds doctor

```
minds doctor [--probe-home <dir>]
```

Checks the setup, one line per check — `ok`, `warn` or `fail` with one line of reason; exit 0 without `fail`, otherwise 1. Checks the agent hook registrations, the Git hooks and the store config (same wording as `minds fsck`), then the witness:

- **Hook binary**: the agent hooks call `minds hook …` through `PATH`; if that `minds` is another
  program than the one running `doctor` (other bytes), `warn` — an older one would not know newer
  setups such as the protected witness and record into the local journal. No `minds` on `PATH`
  is `warn` as well. `minds enable` prints the same warnings. This looks at your shell's `PATH`;
  an agent started elsewhere (e.g. from the Dock) may see another one.
- **Protected witness** (found at its fixed place, see `minds enable`): it answers `ping` (`fail`
  if not) and its home is not readable for you (`ok` on permission denied, `fail` if it opens).
- **Witness observer** (whenever the witness answers `ping`, on every side): the witness's own
  answer to a status request over its socket — `witness observer: watching <root> · <n> frames ·
  last <ts>` (observations appended in this run and the time of the last one). `fail` when it
  reports no file observer (it records only what the agent reports; see `log/witness.err`)
  or does not answer the request (an older binary).
- **Protected witness, not reachable yet** (Linux): set up for this repository, but its group is
  not yet in effect for your session (after your next login) — `warn`, not "not configured".
- **Agent side** (`MINDS_WITNESS_SOCKET` set or `--probe-home` given): the socket variable is set, the witness answers `ping`, and the **isolation probe** — `doctor` tries to open the witness home given with `--probe-home` and the private files in it (non-blocking; a FIFO does not hang it). If anything opens, the result is `fail` ("agent can reach the witness home"). A home that exists but is refused (`EACCES`, e.g. the `user` profile) is `ok` — that is proof. A home that is simply absent (the `container` profile) is only `warn`: absence in another mount namespace proves nothing. On Linux, `doctor` also reads `/proc/self/mountinfo` and fails if a mount exposes the witness home other than its `run/` — a heuristic that does not recognise a mount of a parent directory or a source on another partition, so "nothing found" stays `warn`. Check the container's mounts yourself. An empty `--probe-home` is `fail`, and so is an unclear error (anything but `EACCES`/`ENOENT`/`ENOTDIR`) with `--probe-home`. Without it, `doctor` probes `MINDS_WITNESS_HOME` or the default location: nothing there is at most `warn`, since a missing default path proves little; something that opens is still `fail`. Nothing is read; an opened path is closed immediately.
- **Host side** (`witness.json` in the witness home): profile, pins (`fail` without them), whether the witness answers, the key private, and — for the `container` profile — whether `.devcontainer/` holds exactly the two unchanged templates plus at most their two proposals (`devcontainer.json.minds-proposed`, `compose.yaml.minds-proposed`), all as regular files, and the repository root has no `.devcontainer.json` (`fail` if not). It also looks for code a `git` on the host would run — hooks other than the minds blocks (and `*.sample`), and `.git/config` keys known to run commands (`core.hooksPath`, `core.fsmonitor`, `core.sshCommand`, `filter.*`, `diff.*.textconv`, `include.path`, `!`-aliases and others) — and reports findings as `warn`. This is a heuristic, not proof: a list cannot cover everything an agent can put into `.git` (`commondir`, `config.worktree`, new git keys, nested repositories). Do not run git on the host in a tree the agent wrote. A `.env` at the repository root is a `warn`. If a witness dev container is set up but no witness home is found, that is `fail`, not "not configured". The home is derived from the repository directory itself, never via `git rev-parse` (which follows `core.worktree`). Run it right before every reopen or rebuild of the container. A host-side `ok` is a snapshot of the files, not proof of how the running container was built; an agent-side `ok` comes from a binary running in the agent's environment and is advisory.

```
minds doctor --probe-home /home/alice/.local/state/minds-witness/86f649449fc18941
```

## Daily use

### minds show

```
minds show [<commit>] [--full]
```

Shows the intent and attribution of the session(s) behind a commit (default `HEAD`). The output is compact; `--full` adds the prompt, all files, and edges.

```
minds show HEAD~2 --full
```

The attribution line names only what the record holds: `claude-code 2.0.76 · anthropic/claude-opus-4-1 · 14.2k/3.9k tokens (reported) · 5 files`. The agent version is left out when it was not recorded (never `unknown`), a missing model says `model not recorded`, and the token counts appear only when the transcript was read — `14.2k/3.9k tokens` when the checkpoint read it, `14.2k/3.9k tokens (reported)` when the `SessionEnd` hook read it and passed the sums on; otherwise the segment is left out entirely. A zero that would mean "not read" is a false statement and is not printed; `minds recap` and the TUI (`5.7k tok`, `5.7k tok ◌` for reported counts, nothing when not read) follow the same rule. The prompt is shown without the `<pasted_content>` wrapper Claude Code puts around pasted text.

**Why a model can be missing.** Model, response texts and token counts come from the agent's transcript, not from the hook events. When the transcript was not read, the record says why in `lineage.transcript` — a fixed word, never the path (it holds the user name): `no_path_in_events` (no hook event carried a transcript path), `not_found` (the file was not there at checkpoint time), `not_readable` (it was there, but could not be read — permissions, I/O), `empty` (read, but without an assistant message that names a model), `parse_failed` (read, but no line was a transcript entry), `not_read_by_witness` (the witness built the session and does not load transcripts from agent paths — a decision, not an error), `model_from_hook` (the hook read only the model id from the end of the transcript at `Stop`/`SessionEnd` and passed it on; the model is known, texts and token counts were not read — the case with a witness while the session is still open), `reported_by_hook` (at `SessionEnd` the hook — running as the developer — read the whole transcript once, summed the `usage` fields, took the agent version and the answer texts per turn, redacted the texts with the repository's policy fail-closed, and passed everything to the witness as its own frames; the witness still never opened the file. Version, token counts and texts are then statements of the hook, shown as such: `tokens (reported)`, `◌`), `read_from_slug` (read like `read`, but no event named the path: the checkpoint found the file where Claude Code keeps it, `~/.claude/projects/<slug of the repo root>/<session id>.jsonl`, under the `HOME` of the process that built the session — never imported), or `read`. A record without the field was built by an older binary. `minds inspect` prints the sentence behind the word (`model not recorded — the witness does not read transcripts from agent paths`); `minds show` and `minds recap` print `model not recorded` as well, never the raw placeholder `unknown`.

### minds why

```
minds why <file>:<line> [--full]
```

Shows the session behind a single line, resolved via `git blame` and the session trailer.

```
minds why src/lib.rs:42
```

### minds blame

```
minds blame [--lines] <file>
```

Shows which session is behind which lines of a file, aggregated per session, with context coverage as a percentage. `--lines` prints one annotated row per source line instead — short session id, agent name, line number, and the source text, in file order; lines without captured context carry a `-` in both attribution columns.

```
minds blame crates/minds-core/src/evidence.rs
minds blame --lines src/retry.rs
```

```
src/retry.rs — 3 lines, 1 with captured context (33%)

-                -            1  fn retry() {
b3-a1b2c3d4e5f6  claude-code  2      backoff(3);
-                -            3  }
```

### minds recap

```
minds recap [--limit <n>] [--all]
```

Lists the most recent sessions at a glance. Shows 10 by default; `--limit` changes the count and `--all` shows everything.

```
minds recap --limit 25
```

### minds search

```
minds search <query>
```

Searches the intent, transcript, and files of the captured sessions.

```
minds search "retry backoff"
```

### minds inspect

```
minds inspect [<query> | <file>:<line>]
```

Shows how a change came to be, in the terminal: a session list, the **story** of a session (what the agent did between prompt and commit — the steps in order, with their outcome), and the evidence report of a session. The why chain is no view any more: its links live in *Why this line?* of the Changes tab and in the EVIDENCE block of the Overview detail (`minds why` on the command line still prints the chain; `minds inspect <file>:<line>` opens the Changes tab on that line). On a terminal at least 120 columns wide the list stays in a left column and the story of the session under the cursor is previewed on the right; `Enter` and `e` open Story and Evidence — from 140 columns beside a narrow list (time and headline), below that on the whole screen. Evidence mode (`e`) leads with one sentence for humans — one clause per axis, never an overall verdict: `This session's record is sealed and signed, and all 24 events lie inside the witness boundary. The 95 added lines are reported by the agent; none were observed by a witness. Every tool call was interpreted.` — then the verdict of `minds verify` in its own words (`Verdict of minds verify: ✓ VERIFIED (signatures checked 10:42Z)`, from the same check the Overview shows; before a check it says `sealed, not yet verified — v: run verify`, never VERIFIED; `v` in the view runs that check at once — the same worker and throttle as the Overview — and the view shows `… checking` until the verdict arrives, never a verdict before it). Below, exactly the three axes: `INTEGRITY ◈ record sealed · 1 seal, signed · chain closed (1 epoch) · A1 observed` (seals, signature, chain and assurance level in one line — the level is the one `minds verify` rated once its verdict is in, the same word the Overview shows (`A2 witnessed`), before that the level the repository alone carries; sealed is not verified — the line and the sentence say `✓ record intact` only once `minds verify` has checked the signatures, `✗ TAMPERED` when the seal material was altered), `COVERAGE ✓ complete · 24 events · 0 gaps` with the reconciliation of the commit as a second line in the words of every other tab (`◇ 95 of 95 added lines reported, 0 observed`, `◦ 2 of 48 added lines not observed · 46 reported` — the same count as the Overview and the Changes tab, never "explained"), `INTERPRETATION ✓ all tool calls interpreted`, then `LIMITS` as a sentence for the assurance level (`observed at A1 — no witness ran; …` only when no witness signed; a witness seal the index cannot check says `witness signature not checked here — minds verify --signers rates this seal.`, a witnessed session `witnessed at A2 — …`) and `TECHNICAL (for auditors) ▸ Space`: `Space` unfolds the seal ids, chain roots, algorithm and contexts and what is verifiable outside this host. The detail box follows the cursor — epochs and signature under INTEGRITY, the observation boundary and the per-file reconciliation (unexplained lines named as `not observed in the session`) under COVERAGE, the list of what the level does not prove under LIMITS. Footer line 1 names only the session, its trust strip and the verdict. Live: about once a second it compares HEAD and the tips of every ref under `refs/minds/` (in the code repository and, with a child-repo store, in the store repository) and reloads when they change — a new session, seal, review or an amend appears without a restart. Such an automatic reload recomputes the parts of open views that need a `git` process (artifact reconciliation, the evidence inspector, blame of a line) only when their inputs changed — the commits and claimants of the session, the focused edge, HEAD — and then at most about once a second, so writing unrelated refs does not make the host run `git`; `r` recomputes everything. Cursor, search and the open story or evidence view stay where they were; a view whose session is gone closes with a `closed …` note. `r` reloads immediately. The footer shows `updated HH:MM:SSZ`; `reload failed` with the reason while the previous state stays on screen (the same failing state is not retried every second, only after the next change or on `r`); `live off` when the fingerprint cannot be read; `closed …` when a view could not be recomputed. Strictly read-only. When stdout is not a terminal, lines are emitted tab-separated for `grep`/`fzf`.

**Tabs.** The header shows the tabs in the order of an investigation — what and why → what exactly → how → under which requirement: `1 Overview · 2 Changes · 3 Sessions · 4 Requirements`. `Tab`/`Shift-Tab`, `F1`–`F4` or `1`–`4` switch between them. There is no Verify tab any more: the verdict of `minds verify` stands in the EVIDENCE block of the Overview detail, and `v` runs the check there.

- **Overview** (the start view without a search) — the history of the repository as a commit graph, like GitKraken or `git log --graph`: one colored lane per open branch, merges and forks drawn, newest first, at most 500 commits from HEAD and all local branches; the selection starts on HEAD. It answers three questions: which commit comes from an agent, what was asked, and how far that is backed.
  - **Numbers.** The title counts exactly the rows read — `OVERVIEW · 4 commits · 1 with an agent session` — computed by the reader, so every number can be counted in the list below. No percentages (they hide the denominator); a capped list says `500 commits read (limit)`. "With an agent session" means a captured session is linked: an agent commit made without Minds is invisible to Minds. The second header line is only the breadcrumb; the header names the branch by its short name (`main`).
  - **Rows.** lanes · badge · subject · status · refs · time. The badge is `◉` and the agent's initials (`◉CC` for claude-code) when a session is linked, otherwise the author's initials. The status column shows the state of the **session record** (the seal) with glyph and word — `◈ sealed` only when every seal carries a signature, else `◎ sealed · unsigned`; `! incomplete`, `· unsealed`, `✗ TAMPERED` —, `⚑` when a session names a requirement, `◉n` for several sessions and the review only when it differs from open (`⊕ approved`, `↻ needs work`, `⊘ rejected`). Refs are a quiet text column (`@name`, `▲ HEAD`, `#tag`) — never in the green of evidence, so a branch named like a status cannot pose as one; when space runs out, refs give way first and `▲ HEAD` stays. ### minds recall

```
minds recall <target>
```

Condenses the session(s) behind a file, a line (`<file>:<line>`), or a commit into a short context brief. Deterministic and costs 0 tokens — the agent-facing sibling of `why`.

A file is resolved like `minds blame`: the path is **relative to the repository root**, not to the working directory (`minds recall src/sort.py` finds the same sessions from any subdirectory), and the sessions come from the blame of the whole file — every line to its commit, every commit to its sessions (trailer and store index), in the order the commits first appear in the file — plus the sessions whose record names the file (work not committed yet).

Includes the complete intent request, preserving multiple lines. Terminal output is
sanitized and wrapped to the terminal width (`COLUMNS` or 80 columns as a fallback).

```
minds recall src/lib.rs:42
```

### minds witness init / run / status

```sh
minds witness init --repo /host/project --home /private/witness \
  --path-map /workspaces/project=/host/project [--profile container|user|managed] \
  [--socket-group <group>] [--child-repo <path>] [--policy-rev <rev>] [--intent-key <pub>]
minds witness keygen --home /private/witness
minds witness activate --home /private/witness < request.json
minds witness run --home /private/witness --follow
minds witness status --home /private/witness
```

The Unix-only daemon owns one repository. `init` creates a schema-version-2
`witness.json` and private journal, epoch, key, ledger, log and runtime directories.
Without `--profile`, omitting `--path-map` selects `user` and a map selects
`container`; `container` requires a map, `user` and `managed` refuse one, and
`--socket-group` (name or number; `user` only) lets that group traverse the home
and `run/` (mode 0710) to reach the socket. The map must connect an absolute agent
repository root to the canonical host root. Profile selection alone does not
establish an assurance level. `minds enable --witness` runs `init` for you.

`init` **pins** what the witness trusts, so nothing the agent can edit later
redirects it, and prints what it pinned:

- the canonical git directory (exactly `<root>/.git`; linked worktrees are refused);
- the store: in-repo with the context ref from the repository config (only under
  `refs/minds/`), or a child repository — only when you name it with
  `--child-repo <path>` (outside the observed repository). If the repository
  config selects a child repository you did not name, `init` stops instead of
  pinning a path the agent may have written;
- a witness-owned redaction policy: `.minds/redact.json` from a **commit** —
  HEAD, or the revision you name with `--policy-rev` — preferably the full id of
  the reviewed commit, which the agent cannot redirect (a full id is taken as a
  commit even if a ref of that name exists; ref names like `origin/main` are
  agent-writable locally) — never the worktree. It is read through the pinned git directory
  without config includes and without `refs/replace/*`, size-checked before it is
  read, and verified: commit, every tree on the path and the blob are re-hashed
  from the bytes read and must match their ids (gix does not verify on read, and
  the agent may own `.git/objects`). It is floored at the strict default. Only "the file is not in that commit"
  (or "no commit yet") falls back to the strict default; any other error stops
  `init`. A policy that would redact its own placeholders (e.g. a term like
  `redacted`) is refused — it would make every redacted session unstable. Local
  refs belong to the agent too, so the report names the full commit and blob id
  (also when `init` finds the home unchanged): compare them with the version your
  team reviewed. Trees on the path must be sorted without duplicates (as `git fsck`
  requires), commits and trees are size-limited, and `init` refuses when
  `refs/replace` or `info/grafts` exists — your own `git` would show other content. On a pinned home, a `--policy-rev` whose policy differs is
  refused, not ignored;
- optionally the human's **intent key** (`--intent-key`, a `.pub` line): only a
  security key (`sk-ssh-ed25519@openssh.com`, `sk-ecdsa-sha2-nistp256@openssh.com`, no
  certificate), stored without its comment and shown as `intent key: sk-ssh-ed25519
  SHA256:<fingerprint>`. It is pinned only where none is pinned yet; another key named later
  is reported (`… NOT pinned`) and not stored; a present but unusable entry also counts as
  pinned. Only `--replace-intent-key <pub>` replaces a pinned key — run as the witness user
  in a clean environment (your `PATH` may hold programs the agent placed), e.g. `sudo -k -u
  _minds /usr/bin/env -i HOME=/var/empty PATH=/usr/bin:/bin:/usr/sbin:/sbin GIT_CONFIG_COUNT=1
  GIT_CONFIG_KEY_0=safe.directory GIT_CONFIG_VALUE_0=<root> /usr/local/libexec/minds/minds
  witness init --repo <root> --home <home> --replace-intent-key "<your .pub line>"` (no
  `--socket-group` needed), then compare the printed `intent key: … SHA256:… (newly pinned …)`
  with your security key's fingerprint — the running witness uses it at once (it reads the
  pinned key for every check). Fingerprints (and the
  witness's own `ssh-keygen` calls) use `/usr/bin/ssh-keygen` or the first on `PATH` that,
  with every directory above it, only root can change (no ACL; no sticky exception: in
  `/nix/store` the Nix daemon stores root-owned files for any user), that lies on a file system
  mounted without `nosuid` (a mount a user may make — udisks, FUSE, a disk image — names its own
  owners) and that is named `ssh-keygen` — with an empty environment. A witness whose own binary is not root's (it shares
  your user anyway, e.g. on NixOS) falls back to the `ssh-keygen` on `PATH`; the protected
  witness has none then and fails — on NixOS it is not supported. `init` without a key keeps it.

The running witness never reads `.minds/redact.json` or the store keys in
`.git/config` again. `init` is idempotent: the same configuration is left as it is
(pins included); a different one — including a `--child-repo` other than the
pinned store — is never overwritten, and the error names what differs. A schema-1 `witness.json` (from before the pins) still loads, but the
witness refuses to run or seal with it — fail-closed, since the team's extra
redaction terms would otherwise be dropped silently. Running `init` again with the
same arguments adds the pins (stop the witness first).

`run` requires a generated key and refuses symlinked, foreign-owned or insufficiently
private state. A process lock enforces a single writer even during stale-socket
recovery. Only `run/witness.sock` (0660) belongs in the agent's namespace; keep
the rest of the state directory on the host.

**Intent binding is host-side only (EA-14).** The witness also listens on
`control/control.sock` (socket 0600 in its own 0700 directory, accepting only
connections from the witness user) — never mount it into the agent's domain.
Only there does it accept `IntentActivate`; on `run/witness.sock` the
frame is refused with `intent activation is host-side only`, because a signature
proves who approved a requirement, not that it applies to this session.
`minds witness activate` sends one `IntentActivate` over the control socket of `--home`,
reading `{"anchor": …, "signature": …}` (at most 64 KiB, no other fields) from stdin and
printing the witness's status line — it works only as the witness user.

**Approval by touch (protected witness).** With an intent key pinned, the witness also
accepts an activation on `run/witness.sock` — only with a fresh approval: `IntentChallenge`
returns `nonce <64 hex>`, valid once, on that connection only, for 120 seconds (the connection
stays open that long); `IntentActivateProven` carries anchor, signature, the nonce and a
proof — an SSH signature over `minds-intent-activate-v1\nanchor <anchor id>\nsignature
b3-<hash of the anchor signature>\nnonce <nonce>\n` under namespace `minds-intent-activate` —
and the anchor's own signature under `minds-intent`; both by exactly the pinned key, both with
the user-presence flag set (checked by the witness itself). An approval activates **once**,
measured by the security key's signature counter, which is part of the signed data (a
re-armored or recomputed copy carries the same): the anchor signature's counter must lie above
the highest one the witness has seen for the pinned key (`evidence/intent-counter`), and the
activation proof must be the very next signature (counter + 1), so both touches belong
together. The mark is kept per key (`<counter> <key id>` per line): a newly pinned key counts
from zero, a key pinned again keeps its mark. The new mark is
stored before the activation (if it cannot be, nothing is activated: `approval not
recordable`); the password route raises it too, but only for a signature `ssh-keygen`
verified as the pinned key's — a signature naming the pinned key that does not verify is
refused (`intent signature invalid`), and if it cannot check one (no root-owned `ssh-keygen`,
the 2-second limit, `ssh-keygen` ended by a signal), it activates nothing (`approval not
checkable right now — retry`). The anchor itself is
checked before the mark rises, so a refused anchor does not use up the approval. A security key whose counter steps by more than 1, or a key
with a device-wide counter used for anything else between the two touches, falls back to the
password — and an agent with the key file can provoke that too. If the file is unreadable or
the mark stuck, inspect or remove `evidence/intent-counter` as the witness user. An old approval from
the store plus one hijacked touch therefore binds nothing (`this intent approval was already
used for an activation — sign again`), and an anchor of the agent's would need its own
approval too. A key that reports no counter (0) cannot use this route. Every checked
attempt consumes the nonce. Without a pinned key there is no nonce (`no intent key pinned at
this witness`); clearing (`-`) stays on the control socket. The connection stays open past the
usual 5 seconds only while it is silent (a frame in transit gets 5 seconds from its first
byte); at most 8 connections hold a nonce at once (`too many open approvals at this witness`
— then `sign` uses the password). `ssh-keygen` checks at most one proof per 250 ms, each
check cut off after 2 seconds; a proof that arrives earlier is
answered `too many activation attempts — send it again` and keeps its nonce (the client
resends it, and falls back to the password if the witness keeps deferring). An agent can
provoke that fallback — for as long as it keeps renewing nonces on up to 8 connections, the
touch route stays closed to you: a password
prompt you did not expect is no reason to type it — check what `sign` printed. An old approval
cannot be replayed, and an agent without the human's touch cannot produce a new one. Limits: a touch proves that a human was present,
not what was signed — an agent that can use the key file may start its own `ssh-keygen` and
wait for a touch the human gives for something else (e.g. a signed commit). Use a key for
intents that signs nothing the agent triggers, so an unexpected blink is a warning; with a
key made `-O verify-required` the authenticator also asks for its PIN. The pinned key is
only as good as the comparison of its fingerprint at setup (an agent can write an `sk-` key
whose signatures it makes in software).

The active intent (`evidence/intent.json`) becomes the first chain event of every
new session and is entered as a change into a known session right before its
next hook event; the anchor `-` clears it for new sessions. Per-session
bookkeeping lives in `evidence/folders/*.intent`. `minds intent` (EA-15) is the
client. Without a witness, the local checkpoint binds the anchor id in
`<git-dir>/minds/intent/active` to every session it stores in that run — a
weaker, unchained binding that never carries more than A1. Known limit: in a
profile where the agent runs as the witness user (no
isolation), the agent can reach the control socket too — such a session never
reaches A2 (isolation not proven), but its intent still shows as chained.
Further limits, by design: "from session start" means the first event the
witness saw for that session was a `SessionStart` with `source` `startup` or
`clear` — an agent that bypasses the witness entirely can still present a
fabricated session that way (coverage is the corrective, not the intent).
Clearing (`-`) leaves no trace in sessions already bound. An anchor names no
repository, so anchor and signature can be copied elsewhere. Scope globs are
comma-separated and cannot contain a comma themselves (no `{a,b}`). The
witness checks an activation against its pinned policy; if the repository's
policy differs, an anchor built there can be refused.

**Checkpoint requests run in a worker process.** The witness starts its own binary
(`minds witness __checkpoint`, internal) per request, with a 60-second deadline,
CPU, file-size, open-file and core limits (plus a data-segment limit on Linux), and its own process group. It opens the
pinned git directory once, without following `include.path`/`includeIf`, and reads
tracked paths from the index directly instead of running `git ls-files`. A worker
that blocks (a FIFO swapped in after the layout check, the gix-ref lock loop), dies
(`SIGBUS` from a truncated mapped pack) or overruns the deadline costs only that
request — the witness keeps running and the sessions stay open. At the deadline the
worker first gets `SIGTERM` (it removes the lock files gix holds) and `SIGKILL` two
seconds later; lock files still left behind are named in `log/witness.log`. The
worker's diagnostics reach the witness log through the witness, deduplicated and
redacted; an overlong line is dropped, never cut. The rate limit applies **per
client**, where the client is the requested commit (and the commit the trailers
were retrofitted to): one run per second each, so an agent requesting checkpoints
for its commit every second does not make the human's post-commit request for a
new commit see `rate limited`. A **failed** run blocks every client for that
second, so made-up commit ids get at most one run per second. Every repeated line
in `log/witness.log` is deduplicated within a minute and the count is written
later; a panic prints a fixed line instead of the panic message.

Honest limit: the layout check before a run cannot stop the agent from swapping an
entry inside `.git` for a symlink between the check and the worker's write — the
worker runs as the witness user. Closing that needs file access relative to an open
directory descriptor, which gix does not offer.

Hook frames are parsed and secret-file-filtered using the same code as local hooks.
Each journal append advances a salted, atomically persisted chain. Restart checks
the persisted prefix before completing interrupted updates. `witness.start` records
whether the previous run stopped cleanly; SIGINT and SIGTERM append `witness.stop`.
`--follow` shows sequence, event kind, interpreted tool/path and chain head, without
prompts, arguments or tool responses. Redacted diagnostics go to `log/witness.log`;
the file observer's start (`witness observer: watching <root>`), its failure to start
and its gaps also go to stderr, which the LaunchDaemon writes to `log/witness.err`
(systemd: the journal).
`status` shows the profile, repository, socket health, open hook sessions, most recent
event, key fingerprint and the ten latest ledger entries.

The checkpoint checks the live root before sealing, signs under `minds-witness` with
scope `witness/v1`, records each seal once in the fsynced ledger, and attaches the
standard session trailers. Path mapping affects artifact reads only; stored hook paths
and payloads retain the agent namespace. Host transcripts are never loaded from
hook-supplied paths. Intent requests currently receive `not supported`.

On non-Unix platforms, `minds witness` exits 4 with
`not supported on this platform`.

### minds witness keygen

```
minds witness keygen [--home <directory>]
```

Creates an Ed25519 key at `<home>/key/witness_ed25519` with mode 0600 and
prints its `namespaces="minds-witness"` allowed-signers entry to stdout.
Refuses existing private/public keys and symlinks. Home defaults to
`MINDS_WITNESS_HOME`, otherwise `$XDG_STATE_HOME/minds-witness/<repo-id>`
(`$HOME/.local/state` when XDG is unset). Existing home and key directories
must be private and owned by the current user. No repository is needed when
the home is explicit. See the [verification guide](verification-guide.md)
for trust-file distribution and independent signature verification.

The principal says what the key may vouch for: a witness of the `user` profile
(its own user ID) gets `minds-witness-user@<host>`, every other profile
`minds-witness@<host>`. Only a witness range whose seal verifies under a
`minds-witness-user@` principal can count as separated from the agent (A2) —
list a key under that principal only if its witness really runs under its own
user. A key of a witness under your own user ID (`local`) is readable by the
agent; whatever it signs stays A1 — and so does every session whose hook ranges
it signed, even next to a separated witness. `keygen` prints the separated
principal only if the witness passes the separation checks right then (own user
ID, not an owner of the repository, private home, root- or witness-owned binary),
otherwise the ordinary one with a note; a home whose public key claims the
separated principal without passing them is refused. List each key under exactly
one principal. A key created by an older `minds`
keeps `minds-witness@`; list a separated witness's key again under
`minds-witness-user@<host>`.

### minds verify

Witness-scoped seals require a signature in `minds-witness` by a principal
discovered in the trusted `allowed_signers` file: `--signers`, else `git config --global
minds.signers`, else `~/.config/minds/allowed_signers` (both written by `minds enable`),
else the former `~/.ssh/allowed_signers`; never the repository's git config. The first
line of the output names the file and its source (`Signers ~/.config/minds/allowed_signers
(minds.signers)`). Success prints
`witness-signed (<principal>)`; missing, invalid or incorrectly namespaced
signatures produce `TAMPERED`. Without a signer file, present signatures
print `signature not checked`. See the [verification guide](verification-guide.md).

```
minds verify [<session|rev>] [--signers <file>] [--identity <id>]
             [--commit <rev>] [--require-explained <percent>]
             [--allow-heuristic] [--all]
             [--require-in-scope] [--witness-home <dir>]
             [--require-assurance <A0|A1|A2|A3>] [--limits]
             [--online [--gitlab-url <url>]] [--conformance]
minds verify <session> --sig <file> [--signers <file>] [--identity <id>]
minds verify --evidence <seal-id>
```

Renders the evidence verdict: integrity × coverage across the seals of a session. With no argument, verifies the sessions linked to `HEAD`. A target that is not a session id is resolved as a Git revision (for example `HEAD~1`). Sessions come from `Minds-Session-Id` trailers, falling back to the store's commit-to-session index when no session trailers are present.

Multiple sessions produce the same blocks as individual session checks, separated by a blank line. Exit codes: 0 VERIFIED, 1 TAMPERED, 2 INCOMPLETE, 3 NOT VERIFIABLE, 4 operational failure. The worst result wins in the order **4 > 1 > 3 > 2 > 0**. If HEAD has no linked session, prints `No session is linked to HEAD (<short sha>).` and exits 3. Invalid revisions exit 4.

With `--sig` a session id is required; it checks a signed attribution and exits non-zero when the signature is invalid. `--evidence` yields the verdict for a single seal, even without a session (redaction block).

**Artifact coverage.** The Coverage line also reconciles the commit against the stored write evidence: how many added or modified lines of the commit are explained by the sessions this run verifies, followed by the places that are not.

```
Coverage       complete within the boundary (boundary: agent-hooks/v1 — activity outside it is not captured · 0 gaps · artifact 148/151 lines explained)
  why            3 unexplained line(s): 3 whose last agent claim is another version or a deletion
  unexplained    src/sort/merge.rs:88     the agent's last write or delete of the file shows another version
  unexplained    src/sort/merge.rs:91-92  the agent's last write or delete of the file shows another version
  file only      Cargo.lock               line level unavailable (reconstruction mismatch)
```

- **Which commit.** `--commit <rev>` if given, otherwise the resolved revision (`HEAD` by default); for a session id, the newest commit reachable from `HEAD` (topological order) whose `Minds-Session-Id` trailer names the session. Without such a commit the block prints `Artifact       not assessed (no linked commit)`. In a shallow clone whose first parent is missing, or a partial clone missing a tree or blob, it prints `not assessed (first parent not in this clone (shallow))`, `not assessed (tree not in this clone (partial))` or `not assessed (blob not in this clone (partial))` — verify never fetches. None of these changes the verdict. Objects are read without replace refs (`refs/replace`) and checked against their ids; a replaced object is an error, never a substitute.
- **Which evidence.** Only the sessions whose verdict this run prints contribute claims — the target session, or the sessions of the target revision. `--commit` chooses the commit, not the sessions: `minds verify <session> --commit <rev>` reconciles `<rev>` against that one session. `minds verify <session> --require-explained N` judges the session's own trailer commit, not `HEAD`; to gate `HEAD`, use `minds verify --require-explained N`.
- **Which paths.** Agents record absolute paths. A claim under this checkout's root names exactly that file. In a clone elsewhere (CI), the session's recorded working directory stands in for the root at capture time; because the repository root itself is not recorded, such a claim only counts if it lies below that directory and exactly one candidate path exists in the commit's trees. Deletions — and therefore renames, which count as deletion plus addition — are never explained this way, and sessions started in a subdirectory may stay unexplained outside the capture checkout: fail-closed.
- **Why a line is unexplained.** A `why` line first breaks the unexplained lines down by reason; every place then names its own. The `why` line counts lines, so deletions and removed lines appear only per place. The reasons say only what the linked sessions hold, never who wrote the line:
  - *the agent's last write or delete of the file shows another version*: the last tool claim on the file carries a hash of another version, or is a deletion. It says nothing about when: a session that carries several commits wrote later versions after an earlier commit. When a shell call after that claim mentions the file, `; a later shell command mentions the file (heuristic)` follows.
  - *a tool claim writes the file without a hash*: imported transcripts, redacted content, patches without an after-hash. Whether the agent wrote this version is open.
  - *a write or delete claim ends in this path but could not be mapped to this checkout (not counted)*: a write or delete claim whose recorded path ends in this path (at a path-component boundary) came after any mapped claim on it and could not be mapped to this checkout. It may concern this file or another file with the same trailing path (another repository, for example); Minds does not say which, nor why mapping failed.
  - *the witness's latest readable observation shows another version*: the witness's latest observation with a hash differs from the committed bytes (an opaque observation after it does not change this). This applies even when the last claim carries exactly the committed version.
  - *no tool claim; the witness's latest observation is opaque (no hash)*: the witness saw the file, but its latest observation confirms nothing.
  - *no tool claim; a shell command mentions the file (heuristic)*: a shell call names the path, a path ending in `/<path>`, or the bare file name.
  - *no tool claim or shell mention found*: none of the above. It says nothing about the witness: the TUI and `verify` without trusted signers do not consult witness observations at all. `(search incomplete)` is added, also in the `why` line, when a budget cut the search short.

  The shell heuristic reads the recorded command text. It only looks at words containing `.` or `/`, so `Makefile` never matches, and Windows paths with backslashes are not matched. Its budgets are 64 KiB per call (a word cut at that limit is dropped), 16 MiB per set of sessions, 256 Ki words and 4096 words per file name. It explains nothing: classes, percentages and the gate are unchanged.
- **What "explained" means.** A line counts as explained when evidence backs it — a tool claim whose write-time hash matches the committed bytes (*reported only*), or a witness observation of exactly those bytes (*explained*, *explained (fs only)*). A claim is the agent's own statement, chained into the seals by the hooks; without a valid seal signature (`--signers`) or a witness (EA-08) it is a self-declaration of whoever controls the evidence refs, not an observation. Lines without matching evidence (human edits, shell writes nobody watched) are *unexplained*.
- **Shell writes with a witness.** What the agent writes through the shell (a heredoc, `tee`, `sed -i`, a generator) has no tool payload and therefore no claim. With a running witness the observation still counts: every observation whose time falls in the window of a Bash call — from its `PreToolUse` (minus 2 s of clock slack) to its `PostToolUse` plus 5 s of observer latency — is attributed to that call, and a hash matching the committed blob makes the file *explained* (`●`) with the call as the line's origin (the TUI's WHY box reads `● OBSERVED · written by Bash call 7 · command: cat > src/… <<EOF`). The attribution is by time, not by content: the call *can* have written the bytes. When several calls' windows overlap (parallel calls), the one that mentions the path wins; if none or several do, the file stays *explained (fs only)* — observed, but attributed to no call. A call without a paired `PostToolUse` opens no window, with one exception: the last call of a session that was still open when the commit sealed it (the agent committed from inside the same Bash call) owns everything the witness saw from its start to the end of the session's observations — its `PostToolUse` only arrives after the seal. Sessions recorded before call times existed open no window at all. The mention heuristic below is a different thing: it stays on the claim side and is never shown as an observation. A claim is bound to the bytes it wrote, not to the commit's parent: a linked session that once wrote exactly these bytes explains them, even if a later commit had changed them in between. Contiguous lines are compressed to ranges; at most 20 detail lines are printed, then `… N more (minds verify --commit <rev> --all)`. *file only* marks files judged as a whole (binary, too large, reconstruction mismatch); such a file weighs one line when backed and all of its lines when unexplained. Changes that are not added lines are listed too: deletions, removed lines (a removal not replaced in place, from the base or from what the agent wrote), submodule pointers (also when `.gitmodules` says `ignore`), mode changes, new executables and symlinks. Paths are sanitized before printing (and shortened beyond 256 characters); file contents never appear. Because every verdict-mode run reads the commit's blobs, a damaged object or a replaced object (`refs/replace`) now makes `minds verify` exit 4 even without the artifact flags.

`--require-explained <percent>` (an integer from 0 to 100) turns this into a gate. Observed lines count as explained (*explained*, *explained (fs only)*), as do *reported only* lines; lines that only the shell-mention heuristic speaks for count only with `--allow-heuristic`, which adds them to the gate's numerator — and to nothing else: their class stays *unexplained*, the detail lines still list them, and the assurance is untouched. A line `heuristic      N line(s) counted for the gate by --allow-heuristic: …` says how many the gate took on trust. The gate fails when explained × 100 / changed falls below the requirement (`Gate           explained 98% < required 100%`) and — for any requirement above 0 — when an unexplained change is not captured by added lines: a deletion, removed lines, a binary or oversized file, a submodule pointer, a mode change or a symlink (`Gate           1 unexplained change(s) beyond added lines — required 100%`). A requirement above 0 also fails when nothing can be assessed (no commit, shallow or partial clone, several trailer commits for a session id — pass `--commit`); `--require-explained 0` requires nothing. Only `100` is a hard statement: below it, a large backed file under 2 MiB (a regenerated lockfile) can outweigh unexplained lines elsewhere. A failed gate exits 2 — the same code as VERIFIED, INCOMPLETE, so a pipeline that tolerates 2 also skips the gate; the printed `Gate` line tells them apart — unless the verdict is already 1, 3 or 4, which always win. With several sessions, each block repeats the commit's artifact lines; the `Gate` line appears once at the end.

The gate judges **one commit** against its first parent. A branch with several commits needs one run per commit — otherwise a human commit sandwiched below an agent commit at `HEAD` goes unchecked:

```
for c in $(git rev-list --reverse origin/main..HEAD); do
  minds verify "$c" --require-explained 100 || exit $?
done
```

The flags apply only to the evidence verdict, not to `--sig` or `--evidence`. A human commit without a linked session exits 3 (NOT VERIFIABLE) in that loop — which also stops it.

**Scope findings.** When the session is bound to an intent anchor (`minds intent bind --scope <glob,glob>`) that declares a scope, the Coverage line counts the paths outside it and lists each one with every source that names it:

```
Coverage       complete within the boundary (boundary: agent-hooks/v1 — activity outside it is not captured · 0 gaps · artifact 3/3 lines explained · 1 out of scope)
  out of scope   docs/README.md  (commit, claim)
```

- **Which paths.** *commit*: a changed path of the reconciled commit, including submodule pointers, mode changes and symlinks. *claim*: a write or delete claim of the session that names a path of this repository (claims outside the checkout are beyond the observation boundary, not a scope question). *observation*: a file-system observation of the witness in the session's window, from witness-signed seals only.
- **Glob syntax.** Anchored at the repository root (a leading `/` or `./` changes nothing), modelled on Git's `:(glob)` pathspec: `*` matches within one path segment, `?` one character (never `/`), `**` as a whole segment zero or more segments (`**/x`, `a/**/b`); a trailing `/**` or `/` matches everything inside a directory, not the directory path itself. A glob whose last segment has no wildcard also matches everything inside it, like a pathspec: `src/retry` covers `src/retry/backoff.rs`; `src/*` does not cover `src/a/b`. Dotfiles are not special. Everything else is literal — no character classes, no brace expansion, no escaping; matching is case-sensitive and without Unicode normalization.
- **Which anchor.** The one bound at the end of the verified material. If the witness chained a change of anchor mid-session, the scope is not assessed (see below); without a chained intent (A1), the last locally bound anchor counts — the agent's own claim. Whether a human approved that scope is the Intent line's statement (signature under `minds-intent`, chained by the witness), not this one: combine with `--require-assurance A2` when the scope must not be the agent's own. A2 also brings the witness's file observations: below it, only commit paths and the agent's own claims are checked, and a shell write that never reaches the commit stays invisible. If a witness-signed seal names observations that are missing from this store, or a witnessed session has no closed observation window (an epoch missing, the witness restarted mid-session), or an epoch in the window lost events (gaps), the scope is `not assessed (witness observations incomplete)`. When the intent changed mid-session, the scope is `not assessed (intent changed mid-session)`: which scope governed which work cannot be told apart. Paths longer than 4096 bytes are always out of scope, and so is every path once the matching budget of a run is spent (a fail-closed bound against a hostile scope). Negated globs (`!…`) are not supported: `minds intent bind` refuses them, and an anchor that carries one is `not assessed (negated scope glob unsupported)`. Claim paths with `..` or backslashes (native Windows spellings) count as not resolvable. With several sessions on one commit, each session's scope is checked against all of the commit's paths. Claims are mapped to repository paths as in the artifact reconciliation (another checkout's spelling counts when exactly one candidate exists in the commit's trees, among the changed paths or among the witness's observations); a write or delete claim below the repository root that cannot be resolved (`src/../.github/…`, an ambiguous spelling, a deletion under another checkout's root) makes the scope `not assessed (claim paths not resolvable)`. Only the verified commit is checked — a session spanning several commits needs one run per commit, and with several trailer commits for a session id the gate requires `--commit`.
- No scope declared (`scope=-`) or no bound anchor: the segment and the lines are omitted. A bound anchor missing from this store or unreadable prints `scope not assessed (intent anchor not in this store)` / `(intent anchor unreadable)` instead. When integrity is violated, scope findings are not shown. Findings never change the verdict or the exit code; at most 20 lines are printed, then `… N more (…)`.

**Whose scope.** The session link decides: a revision is judged against the scope of the sessions its `Minds-Session-Id` trailers (or the store index) name, and an agent can write a trailer. A commit that carries the trailer of an older session with a wider scope is judged against that scope. Only `--require-explained 100` shows that the named session actually produced the commit — use both gates together.

`--require-in-scope` turns this into a gate: it fails with exit 2 when any path of any verified session lies outside its scope (`Gate           1 path(s) out of scope — required in scope`) and — fail-closed — when no scope can be assessed, either for a session (`Gate           scope not assessed (no scope declared) — required in scope`) or because the commit is not reconciled (no linked commit, shallow or partial clone). Like the other gates it never masks 1, 3 or 4.

**Assurance and limits.** Below the three axes each block states who observed the material and what it does not prove:

```
Integrity      intact
Coverage       complete within the boundary (boundary: witness/v1 — activity outside it is not captured · 0 gaps · artifact 1/1 lines explained)
  uncorroborated  turn 1 call 1  Write src/sort/merge.rs  b3-deadbeef…  no file-system observation
Interpretation complete
Assurance      A1 observed    (range 1: witness signature not checked — no trusted allowed_signers)
Intent         intent not bound
Not proven     model identity · correctness of the decision · actions outside the boundary (minds verify --limits)
Overall        VERIFIED
```

- **`Intent`** names the session's intent anchor (`minds intent`) as an assurance fact: `intent not bound`, `intent unsigned`, `intent signed, sk key`, `intent signed, software key`, `intent signature not checked` (no trusted signer file, the seal material is not intact, the anchor is not in this store — e.g. not synced yet — or its signature is unreadable) or `intent signature invalid for minds-intent` (also for a malformed `anchor.sig`) — then the anchor (shortened) and whether it is chained by seals verified against a witness principal (`chained`) or not (`unchained`: the local file, or witness seals that could not be verified), plus `intent changed mid-session` or a snapshot mismatch when they apply. The signature is checked over the anchor text under namespace `minds-intent` against the same trusted signer file as the witness (`--signers`, otherwise `~/.ssh/allowed_signers`), and — as for the witness — only for principals whose every line (and every line carrying their key) is restricted to exactly `namespaces="minds-intent"`: an unrestricted developer key, which an agent may reach through ssh-agent, or one restricted to `namespaces="minds"` makes it invalid. `sk key` means the key inside the verified signature is a FIDO key **and** the signature carries the user-presence flag (a key made with `-O no-touch-required` signs without a touch and counts as `software key`); it is a statement about the `allowed_signers` entry, not a hardware attestation. The signature checked is the one stored next to the anchor (`anchor.sig`), not one the witness saw at activation. A valid signature says a human approved this requirement version — not that it was approved for this session: an old approved anchor can be bound again (through the local file, or the control socket in a profile where the agent runs as the witness user). An unsigned or invalid intent never changes Integrity or the exit code — it is not tampering with evidence.
- **`Assurance`** is computed at read time, never stored: `A0 claimed`, `A1 observed`, `A2 witnessed`, `A3 reproduced` — the weakest sealed range of the session. Below A2 the parenthesis names the first reason the level is not higher, with the range it comes from (ranges count from 1 in time order). From A2 on it names the verified witness principal, the profile and the intent signature. Witness signatures count only against a trusted signer file: `--signers`, otherwise `~/.ssh/allowed_signers` — never `gpg.ssh.allowedSignersFile` from the repository — and only for principals restricted to `namespaces="minds-witness"`. The witness profile and its isolation proof are not yet part of the signed material; A2 is therefore not reachable today (`witness profile unknown`). A session linked only through the store index with an inferred (heuristic) edge is `A0`. The level says who observed the session, not whether the session explains the commit — that is the Coverage axis. **A1 is no promise against the agent:** an agent can write its own `agent-hooks/v1` seals, trailers and index edges, so `--require-assurance A1` guards against missing or broken capture, not against a malicious agent; only the witness levels (A2+) are observed outside the agent's control. A signer file the agent can write (one inside the repository, or `~/.ssh/allowed_signers` when the agent runs under your user) makes witness signatures self-attestations — keep the trusted file out of the agent's reach. All seals that name the session count, not only those in its back-reference (`evidence.json`, which the agent can rewrite); a seal found only through the namespace is printed as a `Note`.
- **`uncorroborated`** lists write claims of a witnessed session that no witness observation confirms (same path, same bytes, between 2 s before and 30 s after the claim — the moment the agent reported the write, `written_at`; sessions stored before that field count from the start of the turn). The location is turn and call in the stored session; the hash is the first 8 hex digits of the claimed write-time hash — already stored in the repository and never formed for secret files, but in a job log it lets a reader confirm a guess for a file with very little content. Only sessions with a witness observation window get these lines; they are capped like the artifact lines (`--all`). When the observer was blind in that window — a full channel, a panic, unreadable ignore rules — the line says so instead: `observation gap (overflow: 12 events dropped)`, with the count where the witness could count. An uncorroborated claim does not lower the level and does not change the verdict.
- **`Issue version`** appears only when the bound anchor is a GitLab issue (`minds intent bind --issue`). Without `--online` it reads `not checked (offline)` — never "valid". With `--online` (token in `MINDS_GITLAB_TOKEN`, instance from `--gitlab-url`, `MINDS_GITLAB_URL` or `CI_SERVER_URL` as for `intent bind --issue`) the issue is fetched and its title and description are redacted and hashed exactly as at binding: `current` when they still give the anchor's `content`; otherwise `changed since binding — …` with what the description history says. The history is not assumed: it is asked for over GraphQL (`descriptionVersion.description` of the issue's system notes) and counts only when that instance serves it — `bound version confirmed in description history` (an earlier description, with today's title, gives `content`), `bound version not found in description history` (only when the history is provably complete: every edit has a readable version, the anchor is younger than the first edit, no edit lies within 15 minutes before the binding, and the title has not changed since), `bound version not in the readable description history` (a version deleted or not served; the anchor bound before the first edit — GitLab lists no version for the original description —; bound within 15 minutes after an edit — GitLab merges quick consecutive edits into one note and overwrites its version —; a title change since binding — titles have no versions, so even a matching description is not `confirmed` —; more than 2000 notes; or a 120 s budget spent; timestamps compare by whole seconds, the same second counting as "possibly later"), `no description history available` (older GitLab, no GraphQL, an edition or licence that serves no versions, or a numeric project id) or `description history query failed` (refused, a transient GraphQL error, no answer). A positive result names what it does not say, in parentheses: `redacted spans not compared` (the bound snapshot contains redaction placeholders — a change inside a redacted span looks the same), `stored snapshot does not match the anchor, redaction state unknown`, and `anchor unsigned` / `anchor signature not checked` / `anchor signature invalid` — an agent holding your token can bind an issue itself. A failed check is `version check unavailable (<reason>)` — `unauthorized (HTTP 401)`, `forbidden (HTTP 403)`, `issue not found (HTTP 404)`, `GitLab not reachable`, `MINDS_GITLAB_TOKEN is not set`, a bad instance URL, … The line is a read-time finding: it never changes the Assurance level, the verdict or the exit code, whatever it says. The redaction policy is the worktree's `.minds/redact.json`; a policy changed since binding can make an unchanged issue read as changed.
- **`Not proven`** lists the short forms of the limits that hold at the achieved level, at most three, then `(minds verify --limits)`. `--limits` prints every limit as a full sentence instead. When the last sealed range of a witnessed session ends at a stop but no `SessionEnd` was witnessed (a commit without leaving the agent session), the list ends with `the session's end` (`Not that the session has ended: …`) — information, not a downgrade: A2 requires the session to be quiescent at the checkpoint (last event `Stop`, `SubagentStop` or `SessionEnd`, no open tool call), not ended. A checkpoint that catches the agent mid-work stays at A1 with `session active at checkpoint (PreToolUse #n open)` or `(last event #n is not a stop)`.

`--witness-home <dir>` compares the witness ledger (`<dir>/ledger`, the append-only list of seals the witness produced) with `refs/minds/evidence/`. A seal in the ledger that is missing from the repository makes the block `Integrity      VIOLATED  witnessed seal b3-… missing from the repository` and the verdict TAMPERED (exit 1) — for every session of the run, since the ledger names no session (also when the revision has no linked session). A ledger seal whose ref holds different bytes is reported the same way (`… altered in the repository`). A torn last line (the witness crashed while appending; it appends nothing afterwards) is not counted and prints `Note           witness ledger ends in a torn line — seals after it are not ledgered`. An unreadable ledger, or a line other than the last that is not `<seal-id> <scope> <last_event_at>`, exits 4. The ledger is read, never written.

`--require-assurance <A0|A1|A2|A3>` is a gate on the weakest session of the run: `Gate           assurance A1 observed < required A2 witnessed`, exit 2 — never masking 1, 3 or 4. Any other value exits 4.

```
minds verify --signers ~/trusted/allowed_signers
minds verify HEAD~1
minds verify --require-explained 100
minds verify b3a1f0e --commit HEAD~2 --all
minds verify --signers ~/trusted/allowed_signers --require-assurance A2
minds verify --witness-home "$MINDS_WITNESS_HOME" --limits
```

#### Conformance

With a spec, `verify` adds a `Conformance` block after the session blocks: per rule
*expected → observed → PASS / DRIFT / UNKNOWN*. The first row is the spec itself.

An envelope counts for a commit only if it is **fresh**: its `at` lies in the
commit's history, every descendant of `at` there (the commit included) carries exactly
the signed state (the spec and every pinned schema), and side branches forked before
`at` carry that state or one that existed before `at`. This depends on the history
only, not on the store (which the agent can also write, rewind or empty) — any change
after a signature, even a reverted one, needs a new signature:

- the spec in the commit has a fresh envelope: PASS;
- otherwise DRIFT — a spec changed, removed or broken without a signature, a return
  to an older signed spec (through any number of commits, a removal or a merge), a
  changed schema, a rewound `refs/minds/specs/*`, or a spec signed outside this
  history (after a squash or rebase). To return to an older spec, or after a squash,
  sign again; two differently signed branches that are merged need a signature on
  the result. The rules then come from the newest valid envelope in the history (by
  generation), never from the commit's spec; without one, no rule is evaluated;
- signatures cannot be checked (no signer file, no root-owned `ssh-keygen`, a
  process error) or the history cannot be walked (budget, **shallow clone** — use the
  full history, e.g. `fetch-depth: 0`): UNKNOWN; the commit's rules are shown, marked
  "(unverified spec)".

Without a spec in the commit and without a valid envelope in its history, there is
no report.

The commit is read only through hash-verified, bounded object reads (no `git`
process): entries, path and tree bytes, commit size, parents per commit, file bytes
and schema steps are capped, tree entry names follow `git fsck`, and a symlink or
submodule under a rule's glob is UNKNOWN — a limit or an unreadable object is
UNKNOWN, never PASS. A `graph` rule judges the evaluated commit only (its diff
against the first parent): CI must check every commit of a change, not only its
head. A branch based before a newer signature is checked against the spec of its
own history. Graph facts are at the level of the sessions: at A1 the agent can write
sessions itself; intents count with a valid `minds-intent` signature from the same
signers (`--signers`).

**What the witness saw.** At every checkpoint the witness records, in the signed
observation object, the spec id of the checked commit and the envelopes it found
under `refs/minds/specs/<id>`. Below the rows, `verify` shows one line per spec the
witness saw during the commit's sessions (only sessions linked by trailer or
witness, only trusted witness epochs that carry a session window) — `witnessed
spec b3-… during the sessions (n envelope(s) seen by the witness)`, plus `this
commit is judged against b3-…` if that differs from the spec the rows use. If none
of those envelopes is in the store any more, a `note` line says so. This is
information, not a gate: the witness does not know the trusted signers, so it
records envelopes unchecked, and a new signature legitimately replaces envelopes
without a trusted one. Which spec applies is still decided by history and
signatures alone.

Conformance is a derivation: it never changes the verdict or the exit code.
`--conformance` (for CI) fails with exit 2 on any DRIFT or UNKNOWN, or when there
is no spec; like every gate it never masks 1/3/4. The commit is `--commit`,
otherwise the revision checked. `minds inspect` shows the same rows in the
CONFORMANCE line of the Overview detail (EVIDENCE, for the selected commit) and a
pill per commit in the Overview (computed while idle, for the selected commit and
HEAD).

### minds intent

```
minds intent bind --file <path> [--scope <glob,glob>]
minds intent bind --issue <group/project#iid> [--scope <glob,glob>] [--gitlab-url <url>]
                  [--allow-confidential]
minds intent sign [<anchor-id>] [--key <path>] [--witness-home <dir>]
minds intent show [<anchor-id>]
minds intent list
```

Binds a requirement version and lets a human approve it. `bind --file` hashes the
file like `git hash-object --no-filters` (the raw worktree bytes; with clean filters
such as `core.autocrlf` or LFS an unchanged file still counts as "not in HEAD") and
stores an intent anchor
`source=file:<path>@<blob>` with the redacted snapshot and the expected scope under
`refs/minds/intents/<id>` (synced like everything under `refs/minds/`). The file
must lie inside the worktree; if its version is not in `HEAD`, `bind` warns
`requirement not committed — anchor refers to a working-tree version`. A file the
redaction policy would change gets no anchor: its blob id would be an oracle for
the removed secret — clean the file first. Credential files (`.env`, `.pgpass`,
`.netrc`, `credentials*`, … — the same secret-file wall as capture) and files
ignored by `.gitignore` or `info/exclude` are refused outright, before they are
read: their content is not always something a detector recognizes. Ignore rules
are evaluated in-process like the witness's file observer — case-folded, without
a global excludes file — and no `git` process is started on the repository (its
config, e.g. `core.fsmonitor`, is the agent's). Hard links, FIFOs, symlinks out of the
worktree and anything inside the git directory (also with `--separate-git-dir`)
are refused too; the hard-link and file-identity checks are Unix-only.

`bind --issue <group/project#iid>` binds a GitLab issue in its current version:
`source=issue:<project>#<iid>@<updated_at>` (`updated_at` exactly as GitLab
returns it), and the snapshot is the RFC 8785 canonical JSON
`{"description":…,"title":…}` (a missing description is `""`). Title and
description are redacted **each on its own** before they are put into the JSON —
so a multi-line secret is not hidden behind a JSON escape — and the JSON once more
as a whole; `content` is the hash of that redacted snapshot. If something was
redacted, `bind` warns `the anchor binds the redacted version`. The instance comes
from `--gitlab-url`, otherwise `MINDS_GITLAB_URL`, otherwise `CI_SERVER_URL` —
**never** from `.git/config` (unlike `minds gitlab mirror`): the agent can edit
that file, and a bent URL would send your token to its server and let it serve a
matching issue. Only `https://` is accepted (`http://` only for `127.0.0.1` and `[::1]`). In GitLab CI, `MINDS_GITLAB_URL` wins over `CI_SERVER_URL` — whoever edits the CI configuration controls both (and could reach the token anyway). curl is found through `PATH` (like `ssh-keygen` for signing): an agent that can put its own `curl` first in your `PATH` can read the token — `-q` does not protect against that. curl runs with `-q`, so no `.curlrc` (which an agent under your user could plant: trace files, proxies, redirects) is read, and with `--proto` limited to the instance's scheme and no redirects. The
token comes only from `MINDS_GITLAB_TOKEN` (`read_api` scope suffices); it goes to
curl over stdin, never on a command line, and is removed from every error text.
The output adds `issue   <web_url>`. A confidential issue is refused — its text would be stored under `refs/minds/intents` and pushed by `minds sync` to remotes that may have a wider audience than GitLab allows; `--allow-confidential` binds it anyway (with a warning); a response without the `confidential` field counts as confidential. Issues of private or internal projects are not guarded this way — the same audience question applies before `minds sync` pushes to a remote. 401, 404, a missing token or an unreachable
instance give no anchor. Sign an issue anchor by its explicit id (see below);
`minds verify --online` later checks whether that version still exists.

`sign` signs the anchor text (default: the last bound one) under ssh-sig namespace
`minds-intent` and stores `anchor.sig` next to it. It first prints what is being
approved. The default "last bound" can be written by the agent, so without an
explicit anchor id `sign` only approves a file version that is in `HEAD`; for a
working-tree version, a prompt or an issue anchor it stops and asks for the id
(with the id, a working-tree version gets the warning `this anchor is not the
version in HEAD`). An agent with a shell can commit and bind too: before the
touch, `sign` prints `review  anchor <full id>` and the full blob (or, for a prompt
or issue anchor, its text) on stderr — compare the anchor id with the one your own
`bind` printed, or pass it explicitly. The full content hash is shown as well. Non-ASCII characters in paths are shown
escaped (`\u{430}`). With a software key there is no touch — `sign` signs right
after printing them. The activation path is settled before
the touch: if it is blocked, nothing is signed. The key comes from `--key`, else `git config
minds.intentKey` (the key `minds enable` sets up — `~/.config/minds/intent_ed25519`, a
software key — or pins at a protected witness when it is a security key), else `git config
user.signingkey`; if its `.pub`
is a FIDO key (`sk-ssh-ed25519@openssh.com`, `sk-ecdsa-sha2-nistp256@openssh.com`)
ssh-keygen's "Confirm user presence" prompt is shown (also when the `.pub` is
missing) — a touch an agent with full shell access cannot give. The name in the
`signed` line is the `.pub` comment, display only: `git config user.signingkey`
can come from the repository config, which the agent can edit — `minds verify`
decides who signed. Passphrase prompts are never answered (stdin is
closed; use ssh-agent). Then the anchor is activated, and the last line says
how:

- `active  witness (<profile>)` — sent to the witness's host-side control socket
  (`<home>/control/control.sock`). The home is `--witness-home`, otherwise
  `MINDS_WITNESS_HOME` or the repository's XDG state path when a control socket
  is there. A control socket that does not answer is an error before signing
  (`did not answer — is the witness running`; remove a stale socket if no witness
  should run); a witness that refuses the anchor is an error after it — no
  fallback to the file. The profile is read from the home's `witness.json`: in a
  profile where the agent runs as your user it can fake both socket and file, so
  `active  witness (…)` there is a statement about the home, not proof — `minds
  verify` decides what was bound. A witness running with a home that is neither given nor
  found this way is not seen: `sign` then takes the local file and says
  `no witness`.
- `active  witness (protected, security key)` — the protected witness of this repository
  (`minds enable`, found at its fixed place like the hooks find it; an explicit
  `--witness-home` goes first). Its control socket is closed to you, since the agent shares
  your user. At a protected witness `sign` always signs shielded — whatever the `.pub` claims:
  an `ssh-keygen` from a root-owned directory outside the checkout (as `spec sign`), the text
  over stdin (no temporary file), an empty environment (no `SSH_AUTH_SOCK`), and
  `SSH_SK_PROVIDER` only as `internal` or as the canonical path of a library that, with every
  directory above it, belongs to root — the libraries it loads in turn must be root's too,
  which minds does not check (else it is left out, and `sign` says so — a security
  key then cannot sign there; on macOS that is usually the case: Apple's `ssh-keygen` needs a
  provider, and Homebrew's `libfido2` is user-owned; use a software key, the password
  approves; a software key that lives only in an ssh-agent cannot sign here either — there is
  no agent socket). If the anchor signature is a security key's with a touch (the signature says so,
  not the `.pub`), `sign` asks for a nonce over the witness socket and a **second touch**
  (`Touch your security key again …`) — see *Approval by touch*. It continues with the
  password when no nonce comes (no or another key pinned, an older witness binary, a busy
  socket), when the witness refuses the touch approval (another key, a used approval, a
  counter that does not follow — the reason is shown), when the witness keeps deferring the
  check for 10 seconds (`busy — retrying …`), and when the second touch comes later than 110
  seconds after the nonce. What remains in your own environment (the `minds` on `PATH`,
  `DYLD_*`/`LD_PRELOAD`) is outside what minds can shield.
- `active  witness (protected, approved with your password)` — with a software key (or no
  pinned key), `sign` runs `minds witness activate` as the witness user from the installed
  binary (`sudo -k -u _minds` / `minds-witness`, always asking for your password: a cached one
  does not count and none is left behind). The password is the proof that you, not the agent,
  activate (it proves presence, not the anchor: check what `sign` printed before you type
  it; with Touch ID for `sudo`, a dialog can appear without a terminal, and a `NOPASSWD` sudoers
  rule lets the agent take this route without you). A protected witness
  that does not answer — also one whose service is stopped (its home is there, its socket is
  not) — is an error before signing, never the local file; except on Linux right after the
  setup, when your new group is not in effect yet: then `sign` takes the password route
  directly. `minds witness activate` runs under `env -i` (no `PATH` or `HOME` of yours).
- `active  local file .git/minds/intent/active (A1, unchained — no witness)` —
  without a witness the local checkpoint binds the id in that file to the
  sessions it stores: weaker, the agent can edit the file.

If `MINDS_WITNESS_SOCKET` is set but no control socket is reachable (the agent's
side), `sign` refuses to fall back to the file, which the witness never reads:
run it on the host. The signature is stored even when activation fails.

```
$ minds intent bind --file fachliche-anforderung.md --scope "src/sort/**,tests/**"
$ minds intent sign --key ~/.ssh/id_ed25519_sk
intent  file:fachliche-anforderung.md@3f9c1e2a  content b3-7a41…
scope   src/sort/**, tests/**
signed  patrick@doering-it (sk-ssh-ed25519, user presence)
active  witness (container)
```

Further known limits: the redaction policy is read from the worktree's
`.minds/redact.json`, which the agent can edit (the witness checks against its
pinned policy); and a security key confirms whichever signature request reaches
it first — a concurrent request through a shared ssh-agent can take the touch.

`show` prints the anchor, the full content hash, whether the file version is in
`HEAD`, whether the anchor is still proven (snapshot hashes to `content=`, clean
under the policy), signature presence (not verified there) and the stored
snapshot (not shown when the anchor is not proven); `list` lists
all anchors. The default "last bound" lives in `<git-dir>/minds/intent/last-bound`
— a convenience the agent can write, which is why `sign` shows the anchor before
the touch. `minds verify` checks the signature (see `Intent` above).

### minds spec

```
minds spec sign [--key <path>] [--signers <file>]
minds spec show [<rev>] [--signers <file>]
```

The spec (`.minds/spec.json`, `minds-spec-v1`) is the target state a commit is
checked against — written and signed by a human, never by the agent. Rules:

| Kind | Checks | Example |
|---|---|---|
| `no-dependency` | no crate depends on a forbidden one, also transitively through workspace crates and through renames (`package = …`, `[workspace.dependencies]`); `[dependencies]`, `[build-dependencies]`, `target` forms, not `[dev-dependencies]` | `{"id":"core-is-leaf","kind":"no-dependency","crate":"minds-core","on":["minds-cli"]}` |
| `no-import` | no file under `paths` names a forbidden Rust path: `use` trees across lines and nested groups, a leading `::`, renamed crates; `#[path]`, `include!` and a glob import of a prefix are UNKNOWN | `{"id":"capture","kind":"no-import","paths":"crates/minds-capture/src/**","import":"minds_reader"}` |
| `json-schema` | every file under `files` matches the JSON Schema **in the version that was signed** (a Draft 2020-12 subset; any other keyword is UNKNOWN) | `{"id":"policy","kind":"json-schema","schema":"schemas/replay.json","files":".minds/replay.json"}` |
| `graph` | every commit changing `paths` (default: every commit) carries a minds session (`"expect":"session"`), or binds each of its sessions to an intent with a valid `minds-intent` signature (`"expect":"intent"`; a commit without sessions passes — combine with `session`) | `{"id":"agents","kind":"graph","expect":"intent","paths":"crates/**"}` |

The document is read tolerantly and identified by its canonical form (RFC 8785):
reformatting keeps the id, any change to a rule does not. A rule of an unknown
kind is kept and evaluates to UNKNOWN.

`sign` signs an envelope (`minds-spec-signed-v1`) of the spec in `HEAD` (not the
working tree), the hash of every schema it names (in `HEAD`) and `at` — the `HEAD`
commit — under the ssh-sig namespace `minds-spec`, after printing every rule and pin
on stderr. A FIDO key (`sk-…`) asks for a touch. On Unix only an `ssh-keygen` whose
file and every directory above it are owned by root and writable by no one else is
used (from `PATH` outside the checkout, else `/usr/bin`) — one in `~/.local/bin`,
`~/.cargo/bin` or a user-owned Homebrew prefix could have been planted. Where no
such `ssh-keygen` exists (e.g. only in a group-writable `/nix/store`), signing is
refused and verification is UNKNOWN. The key's
`.pub` file is required: before storing, the signature must come from that key and
cover exactly the envelope under `minds-spec` (`ssh-keygen -Y check-novalidate`).
The policy (`.minds/redact.json`) is read from `HEAD` and never weaker than the
default; a spec it would change is refused. Envelopes are stored under
`refs/minds/specs/<id>` (`envelopes/<hash>/spec`, one file per signature): envelopes
and signatures are added, never replaced (at most 64 envelopes per spec, 32
signatures each — beyond, a changed spec starts anew). Envelopes are never dropped;
of the existing signatures only those from keys on a `minds-spec` line of
`--signers` (default `~/.ssh/allowed_signers`) are kept — without such a line
nothing is dropped. `put` only builds on a ref history that is itself a spec
history. `minds sync` pushes it; fetch it with
`git fetch origin '+refs/minds/*:refs/minds/*'`. `show` prints the id, rules and
whether a stored signature is valid.

`minds verify` accepts a signature only from a principal whose every
`allowed_signers` line is restricted to `namespaces="minds-spec"` — a developer
key in an ssh-agent that the agent can also use does not approve one.

### minds fsck

```
minds fsck [--require-review] [--require-seal]
           [--require-assurance <A0|A1|A2|A3> [--signers <file>]]
```

Checks that every trailer resolves and reports journal gaps. Exits 1 when orphaned trailers exist. `--require-review` also requires an approval for every agent-authored change — a policy gate for CI. `--require-assurance` requires every session that a reachable `Minds-Session-Id` trailer names to reach at least that assurance level (computed as in `minds verify`, with `--signers` as the trusted signer file and without a ledger). Each session below it is listed (`below A2: <session> — A1 observed (range 1: …)`), followed by `Gate           assurance A1 observed < required A2 witnessed`; a failed assurance gate exits 2, any other finding still exits 1. Only sessions named by a reachable trailer are gated: a history without such a trailer passes (the agent controls commit messages — combine with `minds verify --require-assurance` per commit). An invalid level exits 1, like every fsck usage error; `--signers` without `--require-assurance` is refused.

```
minds fsck --require-review
minds fsck --require-assurance A2 --signers ~/trusted/allowed_signers
```

### minds audit

```
minds audit --export [--out <file>] [--base <ref>] [--mode redacted|proof] [--signers <file>]
```

Bundles the provenance chain (change → session → attribution → verdict) into a portable JSON file. It contains the canonical payloads and signatures and is verifiable without this tool. Without `--out` it writes to stdout.

The bundle states its assurance level (`assurance`, the weakest session; each session carries its own) and, under `proves` / `does_not_prove`, exactly the sentences that hold at that level, each with a stable `id` (see [verification-guide.md](verification-guide.md)). `--signers` is the trusted `allowed_signers` for witness signatures (default `~/.ssh/allowed_signers`, never the repo's git config); without them there is no level above A1, and a `--signers` file that cannot be read is an error. The level is the exporter's statement — re-check it with `minds verify --signers` before relying on it.

```
minds audit --export --base origin/main --mode proof --out audit.json
```

## Sync & integration

### minds sync

```
minds sync [--remote <name>] [--detach] [-v]
```

Pushes context and reviews to the remote — all pending refs in one connection, never with `--force`; the only exception is transmitting a GDPR deletion (tombstone ref). Invoked by the pre-push hook; with no new refs the call opens no connection. `--detach` (used by the hook) hands the transport to a background process so the user's push does not wait on it.

```
minds sync --remote origin -v
```

### minds gitlab mirror

```
minds gitlab mirror <subject> --mr <nr> [--url <base>] [--project <id>] [--token-env <var>] [--approve]
```

Mirrors the verdicts of a change to GitLab as an MR note — one-way and idempotent; the repository remains the source of truth. The token is read only from the environment (default `MINDS_GITLAB_TOKEN`), never passed as an argument.

```
minds gitlab mirror I4f2a9c --mr 137 --project 42
```

### minds gitlab webhook

```
minds gitlab webhook [--write] [--secret-env <var>]
```

Reads a GitLab webhook payload from stdin and interprets an MR comment (`/minds approve|reject|needs-work`) as a verdict. Without `--write` it only shows what would be created; the feature is opt-in and runs no service. If `MINDS_GITLAB_WEBHOOK_SECRET` (or the variable named by `--secret-env`) holds a secret, the `X-Gitlab-Token` header is required: the receiver passes it through in `MINDS_GITLAB_WEBHOOK_TOKEN`, the comparison is timing-safe, and on mismatch the payload is discarded.

```
minds gitlab webhook --write < payload.json
```

### minds metrics

```
minds metrics [--format prometheus|openmetrics|json]
```

Exports metrics from the store: throughput, iteration, continuity, streak, redaction, and context coverage. The default format is Prometheus, ready for Grafana.

```
minds metrics --format json
```

### minds render

```
minds render [--out <directory>]
```

Builds a static HTML site from the context (default `./site`): click a line to see the prompt behind it. Stateless.

Each session page reconciles the commits the session takes part in — commits whose trailer names it, or, for commits without a trailer, those linked through the store index (then marked `claims from inferred links (no trailer)`). The reconciliation is per commit: when a trailer names several sessions, all their claims count (`claims of N sessions`), as in `minds verify <rev>`. The page shows `artifact 148/150 lines explained` and a per-file list (`explained`, `explained (fs only)`, `reported only`, `unexplained`). In the changes of the session and on a file page, unexplained lines carry a neutral gutter mark (`◦`, with a screen-reader label `not observed in the session`) — never an error colour. A file page marks lines only while the file at HEAD is byte-identical to the reconciled commit; otherwise the session page shows the marks in the commit's diff. No JavaScript required.

```
minds render --out public
```

## Plumbing — called by hooks, rarely by hand

### minds hook

```
minds hook --agent <name> [--event <name>]
```

Accepts an agent hook event on stdin and stores it in the local journal. Always exits 0.

```
minds hook --agent claude-code --event PostToolUse < event.json
```

### minds checkpoint

```
minds checkpoint [--commit <id>]
```

Interprets the journal, redacts it (policy optionally from `.minds/redact.json`: `allow`, `deny_secrets`, `deny_pii`, `secret_keys`, …), stores the sessions, and appends the Minds session-id trailer to `HEAD`. Invoked by the post-commit hook.

```
minds checkpoint --commit 76a1b3d
```
