1//! Der Kontext-Store: wo Sessions liegen — und was beim Hinlegen zugesichert ist.
2//!
3//! „Speicher ist ein Trait, kein Ort" (Architektur-Prinzip 2 im Plan). Dieses
4//! Crate definiert mit [`ContextStore`] den Vertrag; die beiden Backends
5//! (`InRepoStore` über `refs/minds/context`, `ChildRepoStore` über ein zweites
6//! Repository) folgen in den nächsten Commits und unterscheiden sich nur im
7//! Git-Handle. Deshalb steht hier bereits alles, was für beide gilt:
8//! Kanonisierung, Content-Adressierung, fail-closed und die Prüfung beim Lesen.
9//!
10//! # Die Arbeitsteilung
11//!
12//! Der Trait hat zwei Schichten, und das ist der Kern seines Entwurfs:
13//!
14//! | Schicht | Methoden | wer implementiert sie |
15//! |---|---|---|
16//! | Bytes | [`put_bytes`](ContextStore::put_bytes), [`get_bytes`](ContextStore::get_bytes), [`list`](ContextStore::list) | jedes Backend |
17//! | Sessions | [`put`](ContextStore::put), [`get`](ContextStore::get), [`exists`](ContextStore::exists) | der Trait selbst |
18//!
19//! Ein Backend sieht nur `SessionId → Bytes` und weiß von Redaction, blake3 und
20//! JSON nichts. Die Zusagen liegen dagegen an *einer* Stelle und gelten für
21//! jedes Backend, das je dazukommt — auch für eines, das heute niemand plant.
22//! Wäre `put(&RedactedSession)` eine Pflichtmethode, müsste jedes Backend die
23//! Kanonisierung selbst richtig machen; das zweite Backend, das es falsch macht,
24//! schreibt Sessions, deren ID niemand reproduzieren kann.
25//!
26//! # Fail-closed ist hier ein Typ, kein Vorsatz
27//!
28//! [`ContextStore::put`] nimmt ein [`RedactedSession`](minds_redact::RedactedSession)
29//! entgegen, nicht eine [`Session`](minds_core::Session). Diesen Typ gibt es nur
30//! aus der Redaction-Pipeline — eine ungeredactete Session zu speichern ist
31//! damit kein Policy-Verstoß, sondern ein Compile-Fehler (so von `minds-redact`
32//! vorgesehen, siehe dortige `session`-Modul-Doku).
33//!
34//! Der Preis ist eine Kante am Abhängigkeitsgraphen: `store` hängt zusätzlich an
35//! `redact`. Der Plan zeichnet `core, git ← store`; daraus wird
36//! `core, redact, git ← store`. Kein Zyklus (`redact` kennt nur `core`), und der
37//! Tausch ist es wert: Die Alternative wäre eine Laufzeitprüfung auf
38//! `redaction.applied`, die genau so lange hilft, wie sie niemand vergisst.
39//!
40//! Auf dem **Lese**pfad bleibt sie trotzdem stehen — der Typ überlebt die
41//! Serialisierung nicht, das Flag schon. Siehe [`ContextStore::get`].
42//!
43//! # Zwei Backends, eine Implementierung
44//!
45//! [`InRepoStore`] und [`ChildRepoStore`] sind Hüllen um denselben privaten
46//! `GitStore` — sie setzen nur ein anderes Repository ein. „Gleiches Layout,
47//! separates Repo-Handle" ist damit keine Zusage, auf die man aufpassen muss,
48//! sondern eine, die sich nicht brechen lässt: Es gibt eine Stelle, die Pfade
49//! baut und Refs bewegt. `both_backends_write_the_same_tree` weist nach, dass
50//! zwei Repositories, die nichts voneinander wissen, bei derselben Session auf
51//! denselben Baum-Hash kommen.
52//!
53//! Welches Backend es wird, entscheidet [`StoreConfig`] — an einer Stelle, und
54//! danach sieht alles darüber nur noch `Box<dyn ContextStore>`. Beide Wege sind
55//! erstklassig: ohne Child-Repo landet der Kontext im Repository des Codes
56//! (Default, nichts einzurichten), mit Child-Repo nebenan.
57//!
58//! In **beiden** Fällen bleibt der Trailer im Produktions-Commit — die Nutzlast
59//! zieht um, der Verweis nicht. Deshalb heißt der Zugriff auf das Repository
60//! des Stores [`ChildRepoStore::context_repo`] und nicht `repo`: Es ist beim
61//! Child-Backend nicht das Repo, an dessen Commits Trailer gehängt werden.
62//!
63//! # Was hier bewusst *nicht* steht
64//!
65//! - **Löschen.** Der Store ist ein Audit-Record und damit append-only
66//! (dieselbe Linie wie `minds-git`: kein `remove` auf der Objekt-Ebene).
67//! - **Ein verifizierender Konstruktor für fremde Bytes.** Sollte je ein
68//! Store-zu-Store-Umzug gebraucht werden (In-Repo → Child-Repo), ist das ein
69//! additiver Nachbar zu [`SessionBytes::of`], kein Umbau.
70//!
71//! # Kein `Send + Sync`
72//!
73//! Der Trait fordert es nicht, weil `minds_git::Repo` nicht `Sync` ist (gix
74//! cacht intern beim Lesen). Wer parallel arbeiten will, öffnet pro Thread einen
75//! eigenen Store — dieselbe Regel wie eine Ebene tiefer.

Absicht

Ich möchte M5 so umbauen, dass wir es genauso machen wie entire! Mit dem Hook-Ansatz. Wir bleiben erst einmal bei der Rust implementierung. Diese ist effizienter. Das ist der entscheidende Unterschied. Minds soll auch Hooks installieren im Agenten selbst: Claude Code über `.claude/settings.json`, Codex über `.codex/hooks.json`, Cursor über `.cursor/hooks.json`, Gemini über `.gemini/settings.json`, OpenCode über ein TypeScript-Plugin. Bei Codex wird zusätzlich `codex_hooks = true` in die `config.toml` geschrieben. Dazu Git-Hooks: Checkpoints entstehen, wenn du oder der Agent committen; die Session-Metadaten möchte ich entweder auf einem child-repo haben oder falls wir diese kombination nicht haben direkt im repo. Das Verhalten soll an der Stelle absolut gleich sein.
