1//! [`ChildRepoStore`] — der Kontext liegt in einem **eigenen** Repository.
2//!
3//! Derselbe Baum, dieselben Pfade, dasselbe Ref — nur ein anderes
4//! [`Repo`]-Handle. Das ist keine Beschreibung, sondern die Bauform: Beide
5//! Backends sind Hüllen um denselben [`GitStore`], und
6//! `both_backends_write_the_same_tree` weist nach, dass dabei bis auf den
7//! Baum-Hash genau dasselbe herauskommt.
8//!
9//! # Wofür man das will
10//!
11//! - Das Produktions-Repo bleibt sauber und klont schnell — Transkripte können
12//! groß werden, und niemand will sie bei jedem CI-Klon mitziehen.
13//! - Eigene Zugriffsrechte und eigene Aufbewahrungsfristen für den Kontext.
14//! - Kein CI-Lärm im Parent durch Kontext-Pushes.
15//!
16//! Der Preis ist ein zweites Repository, das existieren, erreichbar und
17//! eingerichtet sein muss. Deshalb ist das In-Repo-Backend der Default und
18//! dieses hier eine Entscheidung.
19//!
20//! # Die eine Regel, die man nicht brechen darf
21//!
22//! **Der Trailer bleibt im Parent-Commit.** Die Nutzlast zieht um, der Verweis
23//! nicht — sonst bricht das Bug-Retrieval, sobald jemand nur den Parent
24//! ausgecheckt hat. Praktisch heißt das: [`ChildRepoStore::context_repo`] ist
25//! **nicht** das Repository, an dessen Commits Trailer gehängt werden. Wer
26//! beides braucht, öffnet das Code-Repo getrennt (`Repo::discover`).
27//!
28//! ```text
29//! Parent-Repo Child-Repo
30//! ├─ Code + Commits mit Trailer → └─ refs/minds/context (nur JSON)
31//! ```
32//!
33//! # Was hier bewusst nicht passiert: anlegen
34//!
35//! [`ChildRepoStore::open`] öffnet ein vorhandenes Repository und meldet
36//! [`StoreError::ChildRepo`], wenn dort keines ist. Es legt keines an. Ein
37//! Store, der bei einem Tippfehler im Pfad stillschweigend ein zweites, leeres
38//! Kontext-Repo erzeugt, verwandelt einen Konfigurationsfehler in
39//! Datenverlust-mit-Ansage. Anlegen und Klonen ist Sache von `minds init` (M6)
40//! — dafür braucht `minds-git` noch ein `Repo::init_bare`.
41//!
42//! # Die Identität wird aus dem Child-Repo gelesen
43//!
44//! `commit_tree_to_ref` besteht auf einer Git-Identität, und gix liest sie aus
45//! der Konfiguration **des Repositories, in das geschrieben wird**. Bei einem
46//! frisch angelegten, baren Child-Repo ohne lokale `user.name`/`user.email`
47//! greift die globale Konfiguration des Entwicklers — und wo es die nicht gibt
48//! (CI-Container, Air-Gap), scheitert der erste `put` mit
49//! `GitError::Identity`. `minds init` sollte die Identität deshalb beim Anlegen
50//! mitschreiben.

62/// Der Kontext-Store in einem separaten Repository.
63#[derive(Debug)]
64pub struct ChildRepoStore(GitStore);

66impl ChildRepoStore {
67 /// Öffnet das Kontext-Repository unter `path`.
68 ///
69 /// `path` zeigt auf das Arbeitsverzeichnis oder direkt auf das
70 /// Git-Verzeichnis; ein bares Repository ist der Normalfall, weil dort
71 /// niemand arbeitet. Es wird **nicht** nach oben gesucht: Ein konfigurierter
72 /// Pfad soll genau das Repository treffen, das dasteht, und nicht
73 /// versehentlich dessen Elternverzeichnis.
74 ///
75 /// # Fehler
76 ///
77 /// [`StoreError::ChildRepo`], wenn dort kein Repository liegt — mit dem
78 /// Pfad in der Meldung, denn das ist die Information, die fehlt.
79 pub fn open(path: impl AsRef<Path>) -> Result<Self> {
80 let path = path.as_ref();
81 Repo::open(path)
82 .map(Self::from_repo)
83 .map_err(|err| StoreError::child_repo(path, err))
84 }
85
86 /// Nimmt ein bereits geöffnetes Kontext-Repository.
87 pub fn from_repo(repo: Repo) -> Self {
88 Self(GitStore::new(repo, DEFAULT_CONTEXT_REF))
89 }
90
91 /// Legt den Ref fest, unter dem der Store liegt (Default:
92 /// [`DEFAULT_CONTEXT_REF`]).
93 ///
94 /// Derselbe Name wie beim In-Repo-Backend, und das ist Absicht: Ein Umzug
95 /// zwischen den Backends soll nichts am Layout ändern.
96 pub fn with_ref(self, reference: impl Into<String>) -> Self {
97 Self(self.0.with_ref(reference))
98 }
99
100 /// Das Repository, in dem der Kontext liegt — **nicht** das des Codes.
101 /// Siehe Modul-Doku.
102 pub fn context_repo(&self) -> &Repo {
103 self.0.context_repo()
104 }
105
106 /// Der Ref, unter dem dieser Store liegt.
107 pub fn reference(&self) -> &str {
108 self.0.reference()
109 }
110}

Absicht

Ich möchte M5 so umbauen, dass wir es genauso machen wie entire! Mit dem Hook-Ansatz. Wir bleiben erst einmal bei der Rust implementierung. Diese ist effizienter. Das ist der entscheidende Unterschied. Minds soll auch Hooks installieren im Agenten selbst: Claude Code über `.claude/settings.json`, Codex über `.codex/hooks.json`, Cursor über `.cursor/hooks.json`, Gemini über `.gemini/settings.json`, OpenCode über ein TypeScript-Plugin. Bei Codex wird zusätzlich `codex_hooks = true` in die `config.toml` geschrieben. Dazu Git-Hooks: Checkpoints entstehen, wenn du oder der Agent committen; die Session-Metadaten möchte ich entweder auf einem child-repo haben oder falls wir diese kombination nicht haben direkt im repo. Das Verhalten soll an der Stelle absolut gleich sein. M5.0 docs: Plan.md — M5 von Transkript-Parsing auf Hooks umgestellt (ADR-0003) M5.1 feat(core): Lineage, Turn.parent/at, ToolCall.effect, Vec<Edge> (additiv) M5.2 feat(capture): JournalEvent + Journal (Datei pro Event, 0600, fsck-fähig) M5.3 feat(cli): minds hook — stdin lesen, anhängen, Exit 0, immer M5.4 feat(capture): Normalisierer Claude Code (SessionStart/Prompt/Tool*/Stop/Subagent*) M5.5 feat(capture): Secretfile-Mauer bei PreToolUse M5.6 feat(capture): Journal + Transkript → Vec<Session> (Turns, Usage, Intent) M5.7 feat(capture): Kanten — Subagent (Observed), Artefakt-Hash, Commit M5.8 feat(cli): minds enable --agent claude-code (settings.json mergen, idempotent) M5.9 test(capture): Fixtures — single, subagent, zwei Agents parallel
