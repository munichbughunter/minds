1//! [`InRepoStore`] — der Kontext liegt im selben Repository wie der Code.
2//!
3//! Das Backend ohne Voraussetzungen: kein zweites Repo, kein Setup, kein
4//! Remote. Wer Minds ausprobiert, klont sein Projekt und legt los; wer im
5//! Air-Gap arbeitet, hat mit dem einen Klon alles beisammen. Deshalb ist es der
6//! Default (siehe [`StoreConfig`](crate::StoreConfig)).
7//!
8//! Die Arbeit macht [`GitStore`]; dieser Typ setzt nur das Repository ein, in
9//! dem auch der Code liegt. Was er zusätzlich mitbringt, sind die Wege
10//! *hinein*: [`InRepoStore::discover`] sucht das Repository so, wie `git` es
11//! tut — von einem Unterverzeichnis aus nach oben. Genau das braucht die CLI,
12//! denn `minds why src/retry.rs:42` wird selten in der Wurzel aufgerufen.
13//!
14//! # Hier sind Kontext-Repo und Code-Repo dasselbe — anderswo nicht
15//!
16//! [`InRepoStore::context_repo`] gibt dasselbe Repository zurück, aus dem auch
17//! die Commits kommen, an die der Trailer gehört. Das verleitet dazu, es für
18//! beides zu benutzen. Beim [`ChildRepoStore`](crate::ChildRepoStore) ist es ein
19//! **anderes**, und ein Trailer, der dort landet, hängt am falschen Commit. Wer
20//! beides braucht, holt sich das Code-Repo selbst (`Repo::discover`) und nimmt
21//! `context_repo` nur für den Kontext. Der Name sagt es — die
22//! Verwechslungsgefahr bleibt trotzdem und ist der Grund, warum er nicht mehr
23//! `repo` heißt.

35/// Der Kontext-Store im Repository des Codes, unter einem eigenen Ref.

39impl InRepoStore {
40 /// Sucht ab `start` aufwärts nach einem Repository — der Weg für die CLI,
41 /// die aus irgendeinem Unterverzeichnis aufgerufen wird.
42 pub fn discover(start: impl AsRef<Path>) -> Result<Self> {
43 Repo::discover(start)
44 .map(Self::from_repo)
45 .map_err(StoreError::backend)
46 }
47
48 /// Öffnet genau `path` — der Weg für Tests und für eine Konfiguration mit
49 /// explizitem Pfad.
50 pub fn open(path: impl AsRef<Path>) -> Result<Self> {
51 Repo::open(path)
52 .map(Self::from_repo)
53 .map_err(StoreError::backend)
54 }
55
56 /// Nimmt ein bereits geöffnetes Repository.
57 pub fn from_repo(repo: Repo) -> Self {
58 Self(GitStore::new(repo, DEFAULT_CONTEXT_REF))
59 }
60
61 /// Legt den Ref fest, unter dem der Store liegt (Default:
62 /// [`DEFAULT_CONTEXT_REF`]).
63 pub fn with_ref(self, reference: impl Into<String>) -> Self {
64 Self(self.0.with_ref(reference))
65 }

67 /// Das Repository, in dem der Kontext liegt — hier dasselbe wie das des

70 self.0.context_repo()

Absicht

Ich möchte M5 so umbauen, dass wir es genauso machen wie entire! Mit dem Hook-Ansatz. Wir bleiben erst einmal bei der Rust implementierung. Diese ist effizienter. Das ist der entscheidende Unterschied. Minds soll auch Hooks installieren im Agenten selbst: Claude Code über `.claude/settings.json`, Codex über `.codex/hooks.json`, Cursor über `.cursor/hooks.json`, Gemini über `.gemini/settings.json`, OpenCode über ein TypeScript-Plugin. Bei Codex wird zusätzlich `codex_hooks = true` in die `config.toml` geschrieben. Dazu Git-Hooks: Checkpoints entstehen, wenn du oder der Agent committen; die Session-Metadaten möchte ich entweder auf einem child-repo haben oder falls wir diese kombination nicht haben direkt im repo. Das Verhalten soll an der Stelle absolut gleich sein.
